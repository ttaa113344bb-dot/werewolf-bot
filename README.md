# بوت لعبة جماعية غامضة وفلسفية على تيليجرام

بوت تيليجرام للعب الجماعي: غموض، نقاش، أدلة، تحقيق، قرارات علنية وسرّية،
ومرحلة فلسفية عميقة — وليست لعبة ذئب أو مافيا. الأحداث والأسئلة تُبنى عبر
الذكاء الاصطناعي من سياق كل جلسة لعب تحديدًا، وتوجد مكتبة محتوى احتياطية
غنية تعمل تلقائيًا إن تعذّر الوصول إلى واجهة الذكاء الاصطناعي، بحيث لا
تتوقف اللعبة أبدًا.

## ما تم فحصه وإصلاحه

المشروع كان غير مكتمل فعليًا: بعض الملفات (`memory.py`, `variety.py`,
`phases.py`, `content_bank.py`) كانت تستدعي دوال قاعدة بيانات (`db.py`)
غير موجودة أصلًا أو بتوقيعات مختلفة، والحلقة الرئيسية في `game.py` /
`app.py` كانت نسخة أبسط لا تستخدم أيًا من هذه الأنظمة. أُعيد بناء المشروع
بالكامل ليصبح متكاملًا:

- **قاعدة البيانات (`db.py`)**: أُعيدت كتابتها بالكامل بجداول
  `games, players, rounds, messages, memories, events, evidence,
  decisions, secrets, game_history, used_content`. كل عملية تُنفَّذ داخل
  thread منفصل (`asyncio.to_thread`) حتى لا تتجمد حلقة أحداث البوت، وكل
  العمليات تمر عبر قفل غير متزامن واحد (`asyncio.Lock`) لمنع تعارض الكتابة
  المتزامنة بين عدة مجموعات في SQLite (كان هذا يسبب توقفات طويلة فعلية عند
  الاختبار قبل الإصلاح — راجع قسم الاختبارات أدناه).
- **التزامن**: لا يوجد أي `time.sleep` يوقف البوت. كل انتظار
  (`asyncio.sleep`) يجري داخل مهمة (`asyncio.Task`) خاصة بكل مجموعة،
  فتستمر بقية المجموعات والأوامر بالعمل بصورة طبيعية أثناءه. تم اختبار
  هذا فعليًا بتشغيل جولتين في مجموعتين مختلفتين في آن واحد، بما في ذلك
  مع أوامر إدارية حقيقية (إيقاف مؤقت، استئناف، تمديد) تعمل أثناء التشغيل.
- **محرك اللعبة (`game.py`)**: أُعيد بناؤه ليدمج فعليًا الأنظمة التي كانت
  معزولة: التنويع (`variety.py`)، اختيار المراحل (`phases.py`)، الذاكرة
  (`memory.py`)، والذكاء الاصطناعي (`ai_engine.py`).
- **الذكاء الاصطناعي (`ai_engine.py`)**: كل نداء له مهلة زمنية وإعادة
  محاولة، ويستخدم ذاكرة مضغوطة بدل تاريخ كامل غير محدود. عند الفشل أو
  غياب المفتاح، يتحول تلقائيًا لمكتبة fallback متنوعة بدل نص أو رسالة
  ثابتة واحدة.
- **الإرسال عبر تيليجرام (`telegram_utils.py`)**: كل رسالة تمر عبر دالة
  إرسال آمنة تقسّم النصوص الأطول من حد تيليجرام (4096 حرفًا) تلقائيًا،
  وتتعامل مع تحديد المعدل (flood control) بإعادة محاولة بعد الانتظار
  المطلوب، ولا تسقط اللعبة كاملة إذا فشل إرسال رسالة واحدة (مثلًا لاعب
  حظر البوت في الخاص).
- **الاستقرار عبر إعادة التشغيل**: عند إقلاع البوت، أي جولة كانت "تعمل"
  في قاعدة البيانات (لأن السيرفر أُعيد تشغيله في منتصفها) تُعلَّم كمنقطعة
  تلقائيًا، وتصل المجموعة برسالة واضحة بدل أن تبقى في حالة متجمدة ظاهريًا.
- **أوامر إدارية إضافية**: `/pause`, `/resume`, `/extend`, `/kick` (راجع
  الجدول أدناه).
- تم اختبار تدفق الانضمام، بدء اللعبة، الجولات المتعددة، القرار السرّي،
  التصويت، الإيقاف المؤقت والاستئناف والتمديد، الإنهاء الإداري منتصف
  اللعبة، إزالة لاعب، الاسترداد بعد الانقطاع، وتشغيل مجموعتين بالتوازي —
  كلها عبر مجموعة اختبارات آلية كاملة (`tests/test_smoke.py`) تعمل بلا
  اتصال إنترنت وبلا توكن حقيقي، ونجحت في تشغيلات متكررة قبل التسليم.

## الاختبارات

```bash
python -m unittest tests.test_smoke -v
```

تعمل هذه الاختبارات بمحاكاة كاملة لـ aiogram وOpenAI (بدون شبكة فعلية)،
وتغطي دورة لعبة كاملة، استقلالية مجموعتين متزامنتين، الإنهاء والإيقاف
المؤقت والتمديد، إزالة لاعب، والاسترداد بعد انقطاع البوت. شغّلها قبل أي
نشر جديد للتأكد أن التعديلات لم تكسر شيئًا.


## فكرة اللعبة

- شاشة بداية واحدة نظيفة مع زر **انضمام** فقط، لا أوامر بدء يدوية ولا زر
  "ابدأ اللعبة".
- كل انضمام يُسجَّل فورًا (ولا يمكن الانضمام مرتين)، ويُغلق التسجيل تلقائيًا
  ويبدأ توزيع الأدوار والجولة الأولى بمجرد وصول العدد إلى الحد الأقصى
  (`GAME_MAX_PLAYERS` في `config.py`) — بلا أي تدخل من المشرف.
- تسلسل حالات واضح لكل مجموعة: `WAITING → JOINING → FULL → STARTING →
  RUNNING → FINISHED`، محمي بقفل خاص بكل مجموعة يمنع أي تعارض إن ضغط عدة
  لاعبين زر الانضمام في اللحظة نفسها (لا تجاوز للعدد، لا بدء مزدوج للجولة،
  لا انضمام مكرر لنفس اللاعب).
- كل جلسة: سيناريو مختلف، أسئلة مختلفة، أسرار مختلفة لكل لاعب (تصل عبر
  رسالة خاصة إن كان اللاعب قد بدأ محادثة مع البوت من قبل).
- مدة النقاش لا تقل عن دقيقتين، وتتزايد فعليًا حسب حالة اللعبة وصعوبتها:
  رقم الجولة (كل جولة أعمق من سابقتها)، عدد اللاعبين (نقاش أوسع)، والأدلة
  المتراكمة (قضية أعقد) — لا برقم ثابت. أثناء النقاش نفسه، إذا استمر
  النشاط الفعلي (عدد الرسائل) مرتفعًا قرب نهاية الوقت، يمتد الوقت تلقائيًا
  بقدر تلك الحيوية، وقد يتكرر هذا أكثر من مرة، حتى سقف 5 دقائق.
- مراحل متغيرة الترتيب: حدث، سؤال، نقاش، فلسفة، دليل، تحقيق، استجواب،
  قرار جماعي، قرار سرّي، تحوّلات علاقات، وأحيانًا تصويت شك غير حاسم.
- نهاية مختلفة في كل مرة (7 أنواع نهايات)، مبنية على ما جرى فعليًا لا
  على قالب ثابت.
- نظام منع تكرار يتتبّع لكل مجموعة على حدة: السيناريوهات، الأسئلة،
  المواضيع الفلسفية، الأسرار، أنواع النهايات... إلخ.

## الأوامر

| الأمر | الوصف | الصلاحية |
|---|---|---|
| `/start`, `/help` | شرح اللعبة وزر الانضمام (اللعبة تبدأ تلقائيًا عند اكتمال العدد) | الجميع |
| `/rules` | القوانين باختصار | الجميع |
| `/players` | قائمة اللاعبين المنضمّين | الجميع |
| `/status` | حالة الردهة/الجولة الحالية (`WAITING/JOINING/FULL/STARTING/RUNNING/FINISHED`) | الجميع |
| `/end` | إنهاء الجولة الحالية بأمان | المشرفون فقط |
| `/pause` | إيقاف مؤقت لكل مؤقتات الجولة الحالية | المشرفون فقط |
| `/resume` | استئناف الجولة من حيث توقفت | المشرفون فقط |
| `/extend [ثواني]` | تمديد وقت النقاش الحالي (افتراضيًا 60 ثانية) | المشرفون فقط |
| `/kick` (كردّ على رسالة اللاعب) | إزالة لاعب قبل بدء الجولة | المشرفون فقط |
| `/difficulty [easy\|medium\|hard\|expert\|impossible]` | عرض/ضبط مستوى الصعوبة قبل بدء الجولة | المشرفون فقط |
| `/myrole` *(في الخاص فقط)* | إعادة عرض بطاقة دورك الكاملة | كل لاعب له دور نشط |
| `/ability` *(في الخاص فقط)* | استخدام قدرة دورك الخاصة (يطلب اختيار هدف إذا احتاجت القدرة ذلك) | كل لاعب له دور نشط |
| `/case` | عرض سجل القضية: الأحداث المهمة، الأدلة، القرارات | الجميع |

راجع `ROLES_AND_ABILITIES.md` لتفاصيل نظام الأدوار الثلاثين والقدرات، و`DEVELOPMENT_REPORT.md`
لتقرير هذه المرحلة من التطوير وخطة المراحل القادمة.

## متغيرات البيئة (الوحيدة المستخدمة)

```
BOT_TOKEN=...        # إلزامي — توكن بوت تيليجرام
OPENAI_API_KEY=...   # اختياري — بدونه يعمل البوت بنظام fallback بلا انقطاع
OPENAI_MODEL=...     # اختياري — افتراضيًا gpt-4.1-mini
DATABASE_PATH=...    # اختياري — افتراضيًا game.db (يقبل أيضًا DATABASE_URL كبديل)
```

عدد اللاعبين الأدنى/الأقصى وأوقات النقاش ثوابت داخل `config.py` مباشرة،
وليست متغيرات بيئة، بحسب الطلب.

## التشغيل محليًا

```bash
pip install -r requirements.txt
cp .env.example .env
# عدّل .env وضع BOT_TOKEN على الأقل
python app.py
```

## النشر

- **Railway / Render**: استخدم `railway.json` أو `Procfile` مباشرة —
  الأمر `python app.py`. اضبط متغيرات البيئة من لوحة التحكم.
- **Docker**:
  ```bash
  docker build -t mystery-bot .
  docker run -e BOT_TOKEN=... -e OPENAI_API_KEY=... -v $(pwd)/data:/app/data mystery-bot
  ```
- **VPS**: `pip install -r requirements.txt` ثم شغّله عبر `systemd` أو
  `screen`/`tmux` أو أي مدير عمليات دائم.

⚠️ قاعدة البيانات SQLite ملف واحد على القرص؛ عند النشر على منصة بدون
تخزين دائم، اربط `DATABASE_PATH` بوحدة تخزين (volume) وإلا ستُفقد البيانات
عند كل إعادة نشر.

## هذه الزيادة (نظام المواجهة 🎭)

أول نظام جديد كامل يُضاف فوق النسخة الأساسية الموصوفة أعلاه، بناءً على طلب
تطوير المشروع نحو "غموض وتحقيق وأدوار سرية متقدمة":

- مواجهة مباشرة بين لاعبَين تُختار عشوائيًا (المتّهِم والمتّهَم) قد تظهر
  ضمن مراحل الجولة العميقة بدءًا من الجولة الثانية، وفقط إن كان عدد
  اللاعبين ≥ `CONFRONTATION_MIN_PLAYERS` (3 افتراضيًا)، ولا تتكرر جولتين
  متتاليتين.
- تسلسل واضح: اتهام (يكتبه المتّهِم في المجموعة) ← دفاع (يكتبه المتّهَم) ←
  رد قصير من كل طرف ← تصويت جماعي "هل كان الدفاع مقنعًا؟" (مقنع / غير
  مقنع / غير متأكد).
- كل مرحلة محصورة فعليًا باللاعب المطلوب منه فقط (بمعرّف المستخدم)؛ رسالة
  أي شخص آخر أثناء نافذة الالتقاط تُسجَّل كنقاش عادي فقط ولا تُحتسب اتهامًا
  أو دفاعًا.
- إن لم يكتب اللاعب المطلوب شيئًا خلال الوقت المتاح، يتولى الراوي (الذكاء
  الاصطناعي، أو مكتبة fallback عند غيابه) توليد نص معقول بدلًا منه — لا
  تتوقف المواجهة أبدًا بانتظار أحد.
- فرصة صغيرة (25%) أن تُسفر مواجهة حادة عن دليل جديد يعقّد القضية أكثر
  بدل أن تحسمها فورًا.
- كل مواجهة تُحفظ في جدول `confrontations` جديد وتظهر ضمن `/case`.
- اختبارات مخصصة في `tests/test_confrontation.py` (10 اختبارات: التقاط
  النصوص، منطق التصويت، الحفظ في قاعدة البيانات، وقواعد اختيار المرحلة)،
  بالإضافة لتشغيل كامل مجموعة الاختبارات القديمة (`test_smoke.py`,
  `test_roles.py`) للتأكد من عدم كسر أي شيء — **28 اختبارًا ناجحًا** إجمالًا.

## ما يحتاج منك تحديدًا

1. **BOT_TOKEN**: أنشئه عبر [@BotFather](https://t.me/BotFather) وضعه في `.env` أو متغيرات البيئة في المنصة.
2. **OPENAI_API_KEY** (اختياري لكن موصى به لتفعيل السرد الذكي الكامل): من
   لوحة تحكم OpenAI. بدونه سيعمل البوت بمحتوى fallback متنوع وليس
   بمحرك ذكاء اصطناعي حي.
3. فعّل **Privacy Mode = Disabled** لبوتك عبر BotFather (`/setprivacy`)
   داخل المجموعات إن أردت أن يقرأ البوت رسائل النقاش الجماعي فعليًا (ضروري
   لتحليل النقاش وحفظه).
4. تأكد أن البوت **مشرف** في المجموعة أو على الأقل يملك صلاحية قراءة
   الرسائل، وأن الأعضاء الراغبين بتلقي أسرارهم/قراراتهم السرّية قد بدأوا
   محادثة خاصة مع البوت مسبقًا (قيد تيليجرام لا يمكن للبوت تجاوزه).

## حدود معروفة

- **الاسترداد بعد إعادة التشغيل تنبيهي لا استئنافي**: لا يُكمل البوت جولة
  كانت شغّالة قبل الانقطاع من نفس النقطة؛ فقط يُعلم المجموعة بوضوح
  ويطلب `/start` لفتح ردهة انضمام جديدة. استئناف حقيقي لمنتصف جولة يتطلب حفظ حالة
  السرد الكاملة، وهذا خارج نطاق هذا الإصلاح.
- **القرارات السرّية والأسرار تصل فقط لمن بدأ محادثة خاصة مع البوت من
  قبل** — قيد من تيليجرام نفسه لا يمكن تجاوزه.
- **قاعدة بيانات SQLite واحدة**: مناسبة لحجم استخدام بوت لعبة عادي؛ إن
  توسّع الاستخدام لآلاف المجموعات المتزامنة بكثافة عالية، الانتقال إلى
  PostgreSQL يصبح منطقيًا (البنية الحالية بجداول وعمليات منفصلة تجعل هذا
  الانتقال لاحقًا واضحًا).

## الرفع إلى GitHub

المشروع جاهز بمستودع Git محلي (تم تنفيذ `git init` و`commit` مسبقًا).
لرفعه لجيت هاب، أنشئ مستودعًا فارغًا هناك (بدون README أو .gitignore
حتى لا يتعارض)، ثم من داخل مجلد المشروع:

```bash
git remote add origin <YOUR_REPOSITORY_URL>
git branch -M main
git push -u origin main
```

لا ترفع ملف `.env` أبدًا إن أنشأته لاحقًا محليًا (موجود ضمن `.gitignore`
فلن يُرفع حتى لو نسيت).
